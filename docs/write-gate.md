# 写入闸门与数据纪元

备份恢复会**整库覆盖**用户的全部数据。如果恢复进行到一半时，一个在恢复之前发起的写操作刚好落库，它就会写进恢复后的数据里——轻则多出一条不该存在的记录，重则外键指向已被清空的账户。

这个 App 用一个很小的机制解决它：`data/WriteGate.kt`。它同时解决另一个问题——**旧界面上的旧操作**。

## 两个概念

**闸门（gate）**：围绕每一个仓储事务的读写锁。

- 普通写入持有读侧，可以并发。
- 恢复持有写侧，独占。
- 恢复开始后，**新来的写入立即被拒绝**（抛 `RestoreInProgress`），而不是排队等待。理由：恢复之后界面会被整体刷新，此刻排队中的操作在语义上已经过期，静静等它执行反而更危险。
- 闸门从恢复**开始**就合上，直到恢复结束（成功或失败）才打开。失败时数据库不变，操作重试即可。

**纪元（epoch）**：数据库里 `app_meta` 表的一个单调递增计数。

- 恢复成功后 +1。
- 每个写操作在**发起处**绑定当时的纪元——ViewModel 创建时、通知或小组件按钮的令牌里、Worker 启动时——然后随协程上下文一路携带。
- 写入真正落库前，比较上下文里的纪元与数据库里的当前值。不相等说明中间发生过恢复，这次操作拒绝执行。

关键在「发起处绑定」而不是「写入时读取」：如果在写入那一刻才读，一个陈旧的操作会因为读到新纪元而蒙混过关。

```kotlin
// 界面侧：在创建时绑定一次
val epoch = container.gate.bound()
scope.launch(epoch) { repo.doSomething() }

// 仓储侧：每次写入都过闸门
suspend fun update(...) = gate.write { dao.update(...) }
```

## 为什么不用数据库锁

Android 上 SQLite 本身能保证单个事务的原子性，但保证不了「跨多个 Await 点的操作」与「恢复」互斥。恢复也不是一个事务就能做完的事：它要读文件、校验、必要时先落盘草稿、覆盖、再重排提醒。闸门把这个跨越多个步骤的过程与其它写入隔开，同时不阻塞读取。

## 写入缺纪元

Debug 包在缺少纪元时直接崩溃，正式包则拒绝写入并提示用户。前者让开发期的问题立刻暴露，后者让用户不会因为一个内部错误丢掉一次操作。

## 相关的恢复细节

- 恢复前会先导出当前数据（「恢复前副本」），并在覆盖前把编辑器里未保存的日记草稿交给协调器落盘，避免恢复把正在输入的文字带走。
- 恢复是整库覆盖，不做合并。这是产品决定：合并两份时间线的余额和流水会引入无法解释的口径问题。
- 恢复完成后，提醒被整体重排——旧的闹钟和通知令牌带着旧纪元或旧 `state_seq`，触发时会被丢弃。
